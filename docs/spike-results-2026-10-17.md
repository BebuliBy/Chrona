# Accessibility spike: фактические результаты 2026-10-17

## Вердикт этапа

**Базовый ручной feasibility-проход завершён на одном SM-A376E/Android16 и текущем YouTube.** Accessibility даёт различимые признаки открытого Shorts; пройдены ограниченные сцены ниже. Это достаточный положительный результат для обсуждения следующего этапа, **не** production-приёмка/числовая точность/всеверсионная совместимость. Ранние этапы и ограничения сохранены хронологически.

## Что установлено

- Label приложения: **Shorts — проверка**.
- Package: `local.habittracker.shortsspike`.
- Label службы: **Shorts — локальная проверка**.
- APK: `app/build/outputs/apk/debug/app-debug.apk` (generated/ignored).
- Consent в приложении, затем самостоятельное включение службы пользователем. Кнопка остановки локального наблюдения отзывает внутреннее согласие; отключить системную службу можно в Settings.
- Только минимальные структурные ID YouTube и переходы/интервалы, без UI-текстов/переписок/скриншотов/сети. JSON в собственном `files/report.json`, доступен через debug run-as только для своей диагностики.
- Начальные marker IDs — **гипотеза**; unit tests проверяют реализацию этой гипотезы, не подтверждают её соответствие YouTube. UNKNOWN — честный fallback.

## Воспроизводимые команды

Из корня проекта с уже установленной средой:

```bash
env JAVA_HOME="$HOME/.local/opt/android-studio/jbr" ANDROID_HOME="$HOME/Android/Sdk" ./gradlew --no-daemon --console=plain :app:testDebugUnitTest :app:assembleDebug
"$HOME/Android/Sdk/build-tools/36.0.0/aapt2" dump permissions app/build/outputs/apk/debug/app-debug.apk
"$HOME/Android/Sdk/platform-tools/adb" -d install -r app/build/outputs/apk/debug/app-debug.apk
"$HOME/Android/Sdk/platform-tools/adb" -d shell am start -W -n local.habittracker.shortsspike/.MainActivity
```

`-d` применять только при ровно одном авторизованном физическом телефоне; иначе выбрать согласованное устройство явно, serial не публиковать. APK reinstall не является разрешением включать Accessibility. Wrapper JAR SHA256: `b3a875ddc1f044746e1b1a55f645584505f4a10438c1afea9f15e92a7c42ec13`; distribution: `b266d5ff6b90eada6dc3b20cb090e3731302e553a27c5d3e4df1f0d76beaff06`.

После consent/включения пользователь проходит Home→Shorts15–20с→выход→обычное видео→блокировку. Разбор только собственного debug report:

```bash
"$HOME/Android/Sdk/platform-tools/adb" -d exec-out run-as local.habittracker.shortsspike cat files/report.json
```

Отчёт не существует до первого исполнения Activity/render или сервиса. Не заменять его чтением общих UI dumps/логов телефона.

## Первый реальный пользовательский прогон

После сообщения «Я всё сделал» read-only ADB подтвердил один авторизованный device и `enabledAccessibilityServices` для собственной службы. Прочитан **только собственный** `files/report.json`, без UI текста/названий видео/данных других приложений.

- Получен реальный положительный кандидат: `reel_player_page_container` из видимых ресурсных IDs YouTube. Остальные начальные candidate IDs этим прогоном не подтверждены.
- Шесть закрытых интервалов-кандидатов: 850,11677,12558,823,3095,4357мс, сумма **33360мс=33,36с**. Это результат эвристики, не ручной ground truth длительности просмотра.
- Между положительными состояниями есть `UNKNOWN/no_validated_player_marker`, включая короткие пропуски. Пока неизвестно, соответствуют ли они реальным выходам/перестроениям UI/пропускам обхода. Не склеивать их молча и не считать весь экран YouTube Shorts.
- Последний сохранённый YouTube snapshot содержит `reel_time_bar`, `view_pager`, `results` и другие структурные ID без главного player marker. Это не автоматически достаточное доказательство Shorts: нужен размеченный контраст с обычным видео/Home.
- В момент чтения последний state — `NOT_SHORTS/youtube_not_foreground`. Не перепутать текущий экран телефона с последним историческим YouTube-снимком.
- Ни ложные положительные/отрицательные, ни погрешность пока не измерены: нет синхронно размеченных контрольных состояний/ручных времён.

Следующий шаг: явно попросить включить/разблокировать телефон и открыть один Shorts, дождаться «Shorts открыт», взять несколько последовательных минимальных snapshot; затем так же размеченно обычное видео/Home/lock. Пользователь просит заранее говорить, когда нужен экран телефона. Сами разрешения агент не меняет.

## Контролируемый положительный сценарий: «Открыт shorts»

Пользователь подтвердил открытый Shorts и получил просьбу оставить один ролик открытым, без переключения/блокировки. Сняты8последовательных read-only snapshots собственного report с интервалом около1с между запросами.

- **8/8 state=SHORTS**, reason=`candidate_player_id:reel_player_page_container`.
- В видимых structural IDs одновременно присутствовали `reel_player_page_container` **и `reel_recycler`**; нижняя навигация не использовалась как evidence.
- Все8snapshots:44обойдённых узла, truncated=false, один одинаковый набор structural IDs; lastSampleElapsedMs увеличивался, т.е. читались новые наблюдения, а не один старый снимок.
- От первой до последней сохранённой временной точки — **8229мс**. Число закрытых интервалов в течение серии не менялось: явного закрытия/дробления этого интервала в серии не обнаружено.
- Это ограниченный положительный результат для неподвижного Shorts на данном устройстве/версии YouTube, **не** оценка погрешности и не доказательство отсутствия ложных срабатываний.

Пользователю предложено выйти из Shorts, открыть обычное длинное видео в основном интерфейсе (не PiP/мини-плеер) и подтвердить «Обычное видео открыто». До этого отрицательный сценарий не считается размеченным/проверенным. Код не менялся.

## Перелистывание с предупреждениями о лимите

Пользователь сообщил, что открыл примерно5роликов и остановился, **но установлен лимит Shorts0минут: перед каждым роликом появляется окно, которое он закрывает вручную**. Это смешанный сценарий: перелистывание и предупреждения, не изолированный swipe test.

- После baseline ordinary-контроля журнал содержит5новых закрытых Shorts-интервалов и один текущий открытый; между положительными состояниями5UNKNOWN/no_validated_player_marker.
- Длительности этих UNKNOWN-периодов:1071,1079,223,362,1799мс. Пять новых закрытых положительных интервалов:5788,7620,4925,5109,9945мс. Не приравнивать число переходов к точному числу роликов или закрытий окон без синхронной разметки.
- На последнем оставленном ролике **4/4свежих snapshots=SHORTS**, открытый intervalесть,43nodes/truncated=false, стабильные reel_player_page_container+reel_recycler. Диапазон свежих sample times3110мс.
- Возможная связь UNKNOWN с окнами лимита пока **гипотеза**. Это не доказанный defect дробления и не разрешение заполнять эти интервалы как просмотр Shorts.
- Код/правила подсчёта не менялись. Лимит не отключали, предупреждения автоматически не закрывали.

Следующий контроль: пользователь перелистывает ещё раз, **оставляет окно лимита открытым**, не блокирует телефон и пишет «Окно лимита открыто». Снять собственные минимальные structural snapshots и сравнить с удержанным Shorts. Источник/вид окна и правило его учёта ещё уточнить, не предполагать автоматически Play/системный/YouTube mechanism.

## Удержанное окно лимита

Пользователь подтвердил «Перелистнул, появилось окно лимита», получил просьбу не закрывать/не блокировать около10с. Сняты8свежих own-report snapshots.

- **8/8UNKNOWN**, reason=`no_validated_player_marker`,0SHORTS/openInterval=false; число закрытых интервалов14стабильно на всей серии.
-22nodes, truncated=false, один structural set; диапазон новых sampleElapsedMs **8326мс**. Исторический Shorts-снимок не выдаётся за текущее окно.
- Видны generic panel IDs `app_engagement_panel`, `close_button`, `header_container`, `horizontal_title_row`, `panel_content_touch_wrapper`; positive player_page_container/reel_recycler отсутствуют. `reel_time_bar` остаётся и здесь — не одиночный маркер Shorts.
- Это доказывает, что удержанное конкретное предупреждение в данном прогоне не начисляет время Shorts. Оно **может** объяснять UNKNOWN-паузы смешанного swipe test, но каждый прежний разрыв отдельно не размечен, поэтому не приписывать все gaps окну как доказанный факт.
- Generic panel/close IDs не объявляются уникальным детектором именно лимита. Код/лимит/автозакрытие/склейка не менялись.

**Открытое продуктовое решение:** предложено не учитывать время закрывающего ролик предупреждения, но пользователь ещё не подтвердил это как окончательное правило. Текущий диагностический UNKNOWN и отсутствие начисления не заменяют принятие требования.

Следующий тест: пользователь сам закрывает предупреждение, держит открытый Shorts≈5с, блокирует кнопкой питания и подтверждает «Телефон заблокирован», не разблокируя до проверки. Не переключать настройки экрана/блокировки через ADB.

## Блокировка из открытого Shorts

После просьбы закрыть предупреждение вручную, оставить Shorts≈5с и заблокировать пользователь подтвердил блокировку. Сняты8последовательных own-report samples и только power-state metadata.

- **8/8NOT_SHORTS**, reason=`screen_off_or_locked`; openInterval=false во всех8замерах, closedIntervals15без роста.
- Последние переходы содержат `SHORTS → NOT_SHORTS/screen_off_or_locked`. Последний interval закрыт с duration6209мс и тем же endReason; это измеренная прототипом длительность, не оценка ошибки относительно ручных≈5с.
- Последовательные sample times обновлялись в диапазоне **8283мс**; отдельное чтение `dumpsys power` подтвердило **Dozing**. При блокировке не использовался старый YouTube snapshot как текущее evidence.
- В этой серии время Shorts при блокировке не начислялось и новый interval не создавался. Это результат конкретного теста **с USB/питанием**, не доказательство долгого Doze/battery behaviour.
- Код/экранные настройки/разрешения не менялись. Телефон блокировал сам пользователь; UI/keyguard/личные данные не читались.

Следом предложено разблокировать, вернуть Shorts (при необходимости вручную закрыть предупреждение), оставить ролик и подтвердить «Разблокировал, Shorts открыт». До этого resume не считается проверенным. Затем нужен отдельный Home/выход из YouTube.

## Возобновление после разблокировки

Пользователь подтвердил «Разблокировал, shorts открыт» и получил просьбу удержать ролик. Прочитаны 8 последовательных свежих snapshots собственного report.

- **8/8 SHORTS**, reason=`candidate_player_id:reel_player_page_container`; видимые `reel_player_page_container` и `reel_recycler` стабильны.
- 46 узлов, truncated=false, один structural set; диапазон обновляющихся sample times **7277 мс**.
- Открытый интервал есть во всех замерах, его начало одинаково на всей серии. Число закрытых интервалов остаётся 15; последний закрытый интервал по-прежнему 6209 мс с причиной `screen_off_or_locked`.
- Последовательность содержит **SHORTS → NOT_SHORTS/locked → SHORTS** с новым началом после блокировки. Текущие данные не объединяют время блокировки с новым просмотром и не перезапускают начало на каждом замере.
- Это подтверждает возобновление в данной сцене, не точную задержку относительно момента разблокировки: ручной timestamp этого момента не зафиксирован.

Код/настройки/разрешения не менялись. Следом пользователь должен нажать Android Home (домашний экран Samsung, не главную YouTube), оставить экран разблокированным и подтвердить «На домашнем экране». До этого уход из приложения как отдельный размеченный сценарий не считается проверенным.

## Домашний экран с оставленным маленьким окном Shorts

Пользователь подтвердил домашний экран, **но уточнил, что маленькое окно Shorts осталось видимым**. Это не чистый уход без видео. Системный PiP против Samsung floating/pop-up mode отдельно не установлен.

- 8 свежих own-report samples за **8122 мс**: **8/8 NOT_SHORTS**, reason=`youtube_not_foreground`, openInterval=false; closedIntervals16 без роста.
- Последний интервал закрыт по `youtube_not_foreground` (167867 мс по журналу; не ручной замер точности). Последовательность включает SHORTS→NOT_SHORTS.
- Последний YouTube structural snapshot был историческим: его возраст вырос примерно45→53с. Он **не** использовался как текущее доказательство содержимого плавающего окна. Содержимое launcher/других приложений не читалось.
- **Обнаружено ограничение:** текущий сервис анализирует `rootInActiveWindow`, а не все видимые YouTube-окна. Плавающее видео без активного YouTube-root в этом режиме **не учитывается**. Это не доказательство, что YouTube/видео не видно, и не успешно пройденная поддержка PiP.
- Если видимый floating Shorts должен учитываться по финальному правилу, данный prototype имеет неполное покрытие/возможный недоучёт. Возможность определить Shorts в таком окне ещё не проверена, расширения доступа/кода не было.

Предложено учитывать видимый Shorts в маленьком окне при разблокированном экране; пользователь ещё не подтвердил правило (**OPEN-WINDOW**). Самостоятельно не выбирать новую семантику и не объявлять режим поддержанным.

Следующее действие пользователя: закрыть маленькое окно, оставить домашний Samsung разблокированным и написать «Окошко закрыл». Только потом получится отдельный чистый Home-контроль. Изменять PiP/лимит/системные настройки или закрывать окна агентом не требуется.

Время предупреждения лимита этим сообщением не определено, OPEN-OVERLAY остаётся открытым.

- 8 свежих own-report samples за **7043 мс**: **8/8 NOT_SHORTS/youtube_not_foreground**, openInterval=false, closedIntervals16 без роста.
- Исторический YouTube snapshot старел примерно291→298с и не считался текущим evidence. Launcher contents не читались.
- В проверенном режиме маленького окна отсутствие начисления соответствует новому правилу; код при принятии правила не менялся. Другие focused/PiP/Samsung pop-up режимы ещё не проверены (OPEN-WINDOW-MODES), универсальная проверка размеров окон не появилась.

**Вывод:** active-root UI-эвристика показала принципиальную пригодность на проверенной конфигурации. Обычное видео не подменяло Shorts, lifecycle-сцены закрывали/возобновляли интервал. Реальный продукт должен честно показывать unknown/coverage и проверять изменения YouTube, а не объявлять эти серии универсальной надёжностью.

Пользователю сообщили, что держать телефон включённым для законченного прохода больше не нужно; предложено вручную остановить локальное наблюдение кнопкой приложения/отключением собственной службы. Факт остановки после рекомендации не проверен. Следующие разработки/тесты требуют выбора конкретного scope; они не запускались.

## Ещё не проверено

Исключение других focused/floating/window modes, pause/reboot/process death/Samsung battery/долгий Doze без USB, изолированный swipe без предупреждения и прочие overlays, погрешность по независимому таймеру, другие версии/устройства/энергопотребление/продуктовые функции. Каждый mixed gap отдельно не размечен. Не подтверждён нулевой false-positive rate для всех экранов YouTube. Сервер/VLESS/бот/регистрация не менялись. Git-ограничения в исторических этапах выше относятся к периоду самого spike до последующего разрешения пользователя.

## Последующие принятые решения и снимок проекта

После базовой проверки пользователь **подтвердил исключение времени предупреждения лимита**: SHORTS-004/DEC-007, прежний OPEN-OVERLAY закрыт. Runtime-код этой сменой требований не изменялся: в проверенном предупреждении он уже не начислял время, а generic UNKNOWN по-прежнему не означает автоматически этот диалог.

Название продукта/Gradle project — **Chrona**. Пользователь разрешил первоначальную отправку текущего prototype/docs и последующие проверенные commit/push в `git@github.com:BebuliBy/Chrona.git`, рабочая ветка `dev`. Предыдущий MyChrona.git заменён до первой отправки, GitHub-репозиторий агентом не переименовывался. История тестов выше сохранена как история, а актуальный Git-порядок — в AGENTS/README.

Полноценная локальная Chrona пока не реализована: сначала обсуждаются scope и контроль UI; предложение в roadmap/architecture не является принятым решением само по себе. Диагностический APK на телефоне не переименован/не переустановлен одной сменой названия. Следующий этап не запускался.
