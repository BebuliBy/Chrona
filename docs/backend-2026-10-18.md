  Внешний Telegram IO выполняется **вне** SQL transaction.

### Identity

- **Независимый API boot:** `TELEGRAM_AUTH_ENABLED=false` явно запрещает создание
  новых Telegram login challenges. Без `BOT_USERNAME` (или с пустым значением)
  этот disabled mode выбирается автоматически; никакого fallback bot name или
  фиктивного t.me URL нет. API health/SQL/core и проверка существующих Bearer
  sessions продолжают работать. Auth begin отвечает **503 TELEGRAM_NOT_CONFIGURED**,
  не создаёт SQL challenge. Для включения — `TELEGRAM_AUTH_ENABLED=true` и реальный
  valid `BOT_USERNAME`; true без valid name является ошибкой конфигурации.
  Если flag отсутствует, valid configured name сохраняет прежний enabled mode.
- Disabled mode ограничивает **новый begin**, не является logout/security bypass:
  status/cancel/exchange существующих challenges по-прежнему проверяют verifier,
  confirmation, TTL, cancellation и one-use consumption. Ранее подтверждённый
  ещё действующий challenge можно безопасно завершить; refresh/revoke/owner auth
  не ослаблены. `migrate` вообще не зависит от Telegram configuration.
- S256 verifier 43–128 unreserved ASCII chars; app обязан генерировать минимум
  256 bits entropy. Challenge TTL **5 минут**, access **15 минут**, refresh
  sliding TTL **30 дней** — технические security parameters, не продуктовые defaults.
- `/start <requestId>` только привязывает pending запрос к одному stable sender
  и ставит prompt в outbox. Явные inline «Подтвердить / Отказать» обязательны.
  Private chat ID должен совпасть с sender ID; group/bot senders игнорируются.
- Atomic one-use confirmed exchange; wrong verifier/request swapping, другой
  Telegram sender, cancel/deny/expiry и replay не выдают session. Status содержит
  только status/expiry, не account/token. Произвольные callback URLs отвергаются.
- В SQL только hashes access/refresh. Refresh rotation сохраняет spent hash;
  reuse **коммитит** revocation всей device session, а не откатывает его вместе
  с ошибкой. Текущая session отзывается отдельно. Owner всегда из Bearer.
- Новый account создаётся после bot confirmation, discoverable=false. Shorts habit
  создаётся системой один раз, `at_most/duration_ms/automatic_shorts`, без цели и
  без выдуманного нулевого actual. Его ID клиент получает через owner pull.
- Rate limits в SQL: challenge 5/device/min + 20/remote-address/min;
  весь `/auth` 120/remote-address/min; search 20/account/min.
  Forwarded headers не считаются доверенными. Это не полная public-edge DDoS защита.

### Raw writes / sync

- Входной JSON разбирается в отдельные transport objects; неизвестные write
  fields отвергаются. `source`, body owner/account не открывают другой scope.
- Все шесть entity types из контракта хранятся durable в `entities` + `change_log`.
  Payload JSON text, не float; FK на habit дополнительно проверяется use case
  **в owner scope**. DB FK защищает account scope; JSON reference не является
  отдельным SQL FK — прямой SQL writer не разрешён.
- Manual habit creation, archive-only update; unit/mode/direction не меняются,
  unarchive/rename/history rewrite не вводятся. Создание automatic habit клиентом
  запрещено. Manual value absolute, без goal cap, одна запись на habit+DayKey,
  optimistic revision. Decimal JSON strings, без exponent/NaN/comma/negative.
- **Пока принимаются только явные текущие DayKey** для manual entries. Прошлые/
  будущие manual writes получают `409 POLICY_UNRESOLVED`: retro-edit policy не
  выбрана. Это fail-closed ограничение checkpoint, не утверждение правила истории.
  IANA zone является частью запрошенного ключа, не выбором общей day policy.
- Goal revisions immutable; requestedFrom не вводит recurrence/наследование.
  В новом read model разрешён только **точный requested DayKey**, как в core
  LocalReadModels; при нескольких запросах этого дня — последняя server append
  revision, не client recordedAt/UUID. Ничего не распространяется на следующие дни.
  AT_LEAST >0, AT_MOST ≥0; zero limit хранится без actual/0.
- Closed intervals/segments immutable, elapsed start/end/duration проверяются;
  bound device ID, boot UUID, allowlisted quality/endReason/observation. Clock
  discontinuity сохраняется явно, wall-clock abs() не заменяет duration.
- Open gap можно один раз закрыть по baseRevision, не менять начало/reason/habit.
- Одинаковый immutable ID+payload — duplicate, другой payload — conflict. Manual
  повтор — SET, не increment. operationId dedup и ack атомарны. Request-level
  Idempotency-Key UUID + canonical JSON: повтор возвращает прежний result;
  другой request с тем же key —409. Batch ordered, per-operation savepoints;
  rejected dependency не создаёт orphan, следующие valid operations обрабатываются.
- Pull — owner-only, сохраняет device/boot/segments только владельцу. Opaque random
  cursor хранится hash+owner+sequence в SQL; invalid/чужой cursor —
  `409 CURSOR_RESNAPSHOT_REQUIRED`. Cursor expiry/GC пока не вводятся, записи
  сохраняются. Page bound 1..500, hasMore/nextCursor настоящие, не client-clock LWW.
- Destructive tombstones/retention не реализованы: `409 POLICY_UNRESOLVED`, не purge.

### Friends / ACL / calculations

- Request/accept/reject/list/remove реализованы общими use cases и доступны HTTP
  и bot. Только адресат отвечает, no self/implicit reverse acceptance.
- Поиск — только `discoverable=TRUE`, без phone/Telegram directory. Все новые accounts
  undiscoverable. **Явный writer реализован:** authenticated `PUT /v1/me/discoverability`
  `{enabled:boolean}` + Idempotency-Key, строгий body, owner из session, SQL transaction/
  request dedup. GET `/v1/me` содержит собственный discoverable boolean. Публичные
  PublicUserDto/search/snapshot не получают flag или private Telegram ID.
- Settings switch клиента позволяет on/off только linked account. Bot `/discover on|off`
  использует тот же application setter с durable inbox dedup. Ни включение поиска,
  ни friendship не создают grants, выключение поиска не отменяет существующую дружбу/
  явные grants. Никакого automatic discovery/SQL flags обхода согласия.
- Matching по sanitized displayName включает актуальный `(@username)`, если username
  присутствовал у sender при **подтверждённом** login. На confirmed login атрибут
  обновляется, consent сохраняется; pending/denied не меняют его. Username не ключ/
  authentication proof и не каталог Telegram; stable identity остаётся Telegram ID.
- Accepted friendship сама ничего не расшаривает. Только owner PUT explicit
  habitIds + resolved time_window + expectedRevision. Неизвестный scope не даёт read;
  defaults не распространяются на друзей/новые habits. Remove friendship атомарно
  убирает оба направления grants. Кэша friend data в backend нет.
- `Social.visibleFacts` — реальный общий ACL projection: сначала разрешённые habits
  и temporal window, затем goals/entries/intervals/gaps/evidence; hidden IDs/names/values/counts
  не входят в результат. Interval projection исключает device/boot/version/endReason;
  segments и tracker health другу не выдаются. Ничего не агрегируется из hidden facts.
- На пересечении **точного закрытого interval/gap с request/grant boundary** нельзя
  честно prorate monotonic duration: остаётся **409 POLICY_UNRESOLVED**, без outside
  timestamps/IDs в error. Это конкретный unsafe boundary, **не** общий запрет view
  из-за неизвестной schedule/coverage policy. Grant никогда не расширяется до
  целого дня/интервала автоматически. Clock-discontinuity record с обоими концами
  внутри scope возвращается с исходным quality, но не участвует в observed sum.
  Open gap с разрешённым start возвращает endUtc=null (даже если ключ не прислал
  writer), без придуманного окончания/длительности/продолжения за scope; open gap
  со start до scope тоже fail-closed409. Никакого ручного закрытия/склейки gaps.
- **Непустой ViewSnapshot теперь200 с полным контрактным DTO**, не глобальный409:
  owner/range/habits/cells/summary/intervals/gaps. Новый `ActivityViews` — одна pure
  function для owner/friend и bot после current ACL. HabitDto/GoalRevisionDto имеют
  revision, nullable поля явные; decimal values — strings, enums lower_snake_case.
  Friend canEditActual/canEditGoal=false. Owner manual actual editable только
  сегодня (сохранён server retro-write guard); архивные клетки read-only.
- Ручной exact-day entry — Known; отсутствие записи — Unknown, не0. Exact-day goal
  даёт planned; без goal — unresolved, не выдуманное not_planned/recurrence. Полностью
  известная клетка получает Ready usagePercent/q/emotion. Streak всегда явно
  unavailable/streak_rules_unresolved. Goal только выбранного habit-day, без
  скрытой истории revisions и без наследования на другой zone/day.
- Shorts: только полностью помещающиеся в день observed intervals дают измеренную
  **Partial** сумму (как core LocalReadModels, end<dayEnd). Same-day segment evidence
  может дать Partial0, но никогда Known0/complete. Нет evidence — Unknown; несколько
  device IDs в разрешённом habit-day — Unknown/multi_device_unresolved, не сложение
  overlapping multi-device totals. Clock/day ambiguity не становится нулём.
  Raw exact timeline при этом остаётся доступен, sanitized без device/boot IDs.
- Из временно разрешённого окна участвуют только intersecting dates. Whole-day
  manual facts/goals доступны лишь если **весь DayKey** внутри scope и zone точно
  совпала; на частичном дне manual actual Unknown/sharing_policy_unresolved,
  goal=null, но разрешённые exact intervals/Partial наблюдения выдаются. Даты за
  scope не попадают в cells/counts/curve points. Owner и friend используют одну
  функцию, не owner summary с последующим скрытием строк.
- Summary plannedCells — только explicit planned клетки; knownCells — только
  planned+Known actual. При unresolved schedule aggregate unavailable/
  schedule_unresolved; при unknown/partial planned actual — unavailable/
  partial_coverage. Эти counters не доказывают полного плана/покрытия. Когда весь
  разрешённый набор известен — реальный mean(q)*100, без компенсации сверхпланом.
  Для пустого набора score unavailable/not_planned, не фиктивные0/100%.
- Individual curves накапливают signed A−G / G−A в собственной unit, general —
  normalized plan_shares. Unknown/schedule gap блокирует дальнейший cumulative
  prefix, а не склеивается с будущим Ready. Известная manual individual curve
  не блокируется partial Shorts другой привычки; +20×7=+140 проверено через view.
  Known A0/G0 at_most даёт q1, usage/zero-emotion unavailable; individual G−A
  определён, general zero-limit coefficient unavailable/zero_limit_curve_unresolved.
- Division MathContext.DECIMAL128 (34 digits, HALF_EVEN) для usage/mean/curves.
  q использует exact comparisons и 34 digits **DOWN**, как актуальный core Scoring:
  tiny deficit/violation не округляется в q1. Emotion boundaries — exact cross-products.
  Это вычислительная точность, не изменение raw фактов/продуктовый cap.

## 3. Telegram worker: что реально работает

- Реальный adapter `SocksTelegramTransport` на OkHttp, fixed
  `https://api.telegram.org`, explicit SOCKS proxy. Принимает **только**
  `socks5h://host:port`, без proxy auth/paths/query/direct fallback/redirects.
  SOCKS route создаёт unresolved destination; fake proxy test проверяет SOCKS5
  **ATYP=domain + telegram.invalid**, а не только наличие proxy setting.
  Local DNS для Telegram destination дополнительно запрещён в Dns adapter.
- Bot token читается только при runtime bot startup из файла. Не env value, не argv,
  не fixture/response/log. Нет HTTP logging interceptor, token-bearing URLs/cause
  не пробрасываются в ошибки. Fake transport/token явно названы FAKE_TEST.
- `getUpdates(timeout=5, limit=50, allowed_updates=[message,callback_query])`,
  connect5/read12/write5/call20 секунд. Нет обязательного sleep после успешного poll;
  обработка inbox/outbox между poll означает, что это **не жёсткое SLA 5 секунд**
  при очереди исходящих сообщений.
- Одна SQL lease 45 секунд + уникальный holder. Старый holder не poll/commit после
  потери lease. Durable inbox и next_offset коммитятся вместе до следующего poll;
  обработка business action/outbox/processed flag атомарна. Restart не теряет
  подтверждённый offset/action/dedup. Неизвестные сообщения сохраняются только как
  noop+updateId, не raw text/whole Telegram update.
- Network poll backoff exponential 0.5..30s + jitter≤25%; 429 retry_after 1..3600s
  + jitter. Во время длинного ожидания прогресс/lease обновляются каждые5s.
  Outbox retry SQL-backed 1s..~34min exponential (upper ceiling1h) + jitter, 429
  отдельно; повторная отправка view всегда заново проходит ACL. Revoked/unresolved
  data job discarded; вместо stale data ставится безопасная ошибка.
- **Business effects exactly-once относительно updateId; Telegram sendMessage —
  at-least-once.** Bot API не имеет idempotency key: crash после принятия sendMessage,
  но до SQL ack может дать повтор сообщения. Не заявляется невозможное exactly-once
  external delivery. Уже отправленное не отзывается. ACL read имеет точку проверки
  перед отправкой; уже находящийся в сети запрос не отозвать задним числом.
- Bot команды для проверки адаптера: `/start UUID` + inline confirmation,
  `/friends`, `/requests`, `/request accountUUID`, `/accept requestUUID`,
  `/reject requestUUID`, `/view ownerUUID fromDate toDate IANAzone`.
  Это минимальный технический интерфейс, не согласованный финальный UX бота.
- `/view` теперь использует тот же полный `ActivityViews` snapshot, что HTTP.
  Маленький ответ — canonical JSON одним сообщением; длинный — JSON fragments
  с `[part/total]` header, до3500 UTF-16 code units без разрыва surrogate pair.
  Следующий fragment ставится в durable outbox только вместе с SQL ack предыдущего.
  **Перед каждым fragment и retry** заново строится current ACL-filtered snapshot;
  snapshot hash проверяет стабильность данных. При изменении/revoke дальнейшая
  отправка прекращается с явной ошибкой, не смешивает revisions/не шлёт stale data.
  В SQL хранятся только request/part/hash, не разрешённая копия приватной статистики.
  Это технический текстовый bot view, не финальный графический UX. Friends/requests
  пока ещё имеют size bound с явным NOT_IMPLEMENTED, не silent truncation.
- Readiness требует свежих progress и successful poll (<45s), действующую lease,
  доступную DB и отсутствие pending failed outbox deliveries. Отдельный
  monotonic watchdog при отсутствии progress>60s завершает процесс кодом70
  (проверка каждые10s). Network outage даёт not-ready/backoff, не бессрочный
  блокирующий socket. Необработанная ошибка worker завершает process70 для restart.
  Зависание самого watchdog/всего host этим не лечится.

- Bytecode17 допускает отдельно проверенный официальный JRE21 как альтернативный
  runtime-кандидат, **не** автоматическую замену image. Установки JDK/OS не нужны

- Никаких AVX2/native compiler flags/`-march=native`. Реальный non-AVX2 amd64 host,

  Теги в Dockerfile — candidate, не уже принятые/проверенные production digests.

  отдельный API процесс; нужен запас на native buffers/threads сверх heap. CPU/RSS/
  startup latency не измерены; лимит container memory нельзя приравнивать к Xmx.

### Entrypoint / modes / mounts

`/opt/chrona/bin/chrona-backend api|bot|migrate|healthcheck`.

- `api`: application routes + health, default127.0.0.1:8080. Больше не требует
  BOT_USERNAME/token/proxy для старта; достаточно DB configuration и db-password.
  API readiness — доступность SQL/core, не утверждение готовности Telegram login.
- `bot`: **только** management health, default127.0.0.1:8081; исходящий Telegram
  исключительно через независимый proxy service. Product HTTP routes не публикуются.
  Всегда требует valid BOT_USERNAME, telegram-token file и TELEGRAM_PROXY, даже
  при TELEGRAM_AUTH_ENABLED=false. Без файла токена startup завершается ошибкой,
  worker/readiness не запускаются. Имя не угадывается и через getMe не добывается;
  реальность конфигурации требует отдельно разрешённого Telegram smoke.
- `migrate`: проверить/apply миграции в заданной **собственной** Chrona DB и выйти.
  BOT_USERNAME/telegram-token/auth feature configuration для миграций не нужны.
  Также api/bot startup вызывает ту же migration routine. Это важный side effect:
  запуск против реальной DB требует разрешения/backup; роль DB в этом v1 имеет DDL.
- `healthcheck`: встроенный JRE HTTP probe `http://127.0.0.1:$PORT/health/ready`,
  connect/read2s, без чтения secrets/DB password. Default PORT8080, поэтому для bot
  **явно выставить PORT8081**. Docker HEALTHCHECK30s, start-period30s, timeout10s,
  retries3. В image не требуются curl/wget/новые OS packages.
- UID:GID **10001:10001**, read-only application `/opt/chrona`; secrets read-only
  mount `/run/secrets/chrona`. Файлы доступны uid10001 (например0400 owner10001),
  parent directory traverse, без world-readable secret values.
- Runtime files: `db-password` обязателен для api/bot/migrate; `telegram-token`
  **только bot**. Без лишних secrets mounts в API/build. Значения не помещать в
  env-file/argv/image/Git. Token file сейчас отсутствует и не читался.
- Persistent state — общая PostgreSQL database/volume; отдельный app data mount
  не нужен. Для read-only rootfs нужен writable ephemeral `/tmp` для JVM/Netty.
  Ни Docker/DB volumes, ни actual mount permissions этим проходом не созданы.

### Env-file schema

Пример: `backend/runtime.env.example`, **только placeholders/non-secret values**.

| Env | Смысл |
|---|---|
| `SECRETS_PATH` | Абсолютный путь к read-only directory; единственная ссылка на secret values |
| `DB_URL` | `jdbc:postgresql://chrona-db:5432/chrona`, без password/userinfo; H2 production fallback запрещён |
| `DB_USER` | Dedicated Chrona SQL role, default chrona; не Nextcloud/чужая DB |
| `TELEGRAM_AUTH_ENABLED` | true/false; для API сейчас явно false. Если отсутствует — false без имени, true при configured имени. Управляет новым auth begin, не отключает проверки существующих sessions/challenges |
| `BOT_USERNAME` | Для API disabled и migrate не обязателен. Обязателен для enabled auth и bot mode: имя реально созданного владельцем бота, без @/URL, не token; placeholder не подставляется |
| `TELEGRAM_PROXY` | Для bot обязательно `socks5h://xray-proxy:10808`; private infra service, не host localhost другого контейнера |
| `BIND_ADDRESS` | Default127.0.0.1; только явное infra override для private container network |
| `PORT` | API8080, bot8081; отдельное значение для каждого процесса, также используется healthcheck |
| `JAVA_OPTS` | Несекретные JVM limits/log level; пример -Xms32m -Xmx256m …warn |

Запрещены token/password env values: BOT_TOKEN/TELEGRAM_TOKEN/TELEGRAM_BOT_TOKEN/
DB_PASSWORD. Proxy credentials не поддержаны. Не добавлять ALL_PROXY как замену
явному adapter setting. API DB не туннелируется этим proxy автоматически.

**Точный handoff для текущего API без созданного бота:** задать
`TELEGRAM_AUTH_ENABLED=false`, не задавать BOT_USERNAME и не монтировать bot token.
DB/SECRETS_PATH/db-password, private bind и PORT остаются как прежде. При отсутствии
и имени, и flag получится тот же safe mode. Позже для реального login установить
на API true + фактическое имя после подготовки bot worker; SQL migration не требуется.

### Bind / network / lifecycle

- На первом host запуске **loopback/private**, без автоматического публикации
  наружу. Для Docker private network sysadmin может явно задать BIND_ADDRESS=0.0.0.0
  внутри контейнера; host publish API при необходимости только
  `127.0.0.1:8080:8080`. `EXPOSE` в Dockerfile не является publish.
- Bot8081 — private management only; PostgreSQL5432 и SOCKS10808 не публиковать
  публично. DB/proxy используют независимые private infra services. Изменения
  global route/TUN/DNS/существующих host services код не делает.
- `/health/live` — process HTTP loop; `/health/ready` — DB и для bot свежий poll/
  progress. При DB/network failure503. Health endpoint body без credentials.
- Docker restart policy задаёт sysadmin (например согласованный unless-stopped).
  **Docker unhealthy сам не рестартит контейнер**. Встроенный watchdog превращает
  worker stall в exit70; внешние monitoring/restart/alerts всё ещё нужны.
- SIGTERM JVM shutdown hook освобождает bot lease; при crash lease истечёт45s.
  Применять rolling replacement без принудительного запуска второго poller.
  Secrets rotation в v1 требует restart bot/процесса, hot reload не реализован.
- Backup/restore — отдельная infra задача (вся Chrona DB, не только entities).
  До upgrade backup + staging migrate/restore smoke. Откат V001 — restore backup,
  автоматический destructive down migration не поставляется.
