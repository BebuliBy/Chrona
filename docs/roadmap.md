## Ближайшие зависимости

1. Основной SM-A376E/Android16/API36 и текущий YouTube проверены, сервис пользователь включил сам; базовые real UI/lifecycle-сцены пройдены. На A33(2022) друга тестов не было, ОС неизвестна.
2. Предупреждение лимита исключено пользователем(SHORTS-004), название Chrona принято. До полноценной локальной реализации согласовать предложенный ниже scope/UI, числовую точность/правила интервалов/timezone. Исключение маленького окна проверить в иных режимах перед обещанием универсального покрытия.
3. Телефон для законченного прохода больше держать активным не нужно; пользователю предложено остановить локальную диагностику. Для следующих тестов заранее сообщать нужное состояние, дождаться согласия/подтверждения, не включать разрешения через ADB.
4. До запуска новых скачиваний/установок/системных действий оценить их scope; текущие документы не являются неограниченным разрешением.
5. Сохранять результаты со сведениями об устройстве/версиях и ограничениями; только после фактических тестов менять статус proof.

Код/Gradle/debug APK,8unit-тестов и базовый контролируемый проход есть. Погрешность/длительная автономность/reboot/process death/версии/прочие windows не проверены. Бот/backend/VPN и полноценная локальная версия не реализованы. Пользователь разрешил Git workflow: `dev`, актуальный origin `git@github.com:BebuliBy/Chrona.git`, проверки/осмысленные commit/push по AGENTS; это не разрешает все предложенные функции.

## Локальная Chrona: выбран вариантБ, детали уточняются

Пользователь выбралБ из предложенного локального scope. Высокоуровнево приняты ручные привычки/цели/серии вместе с Shorts; полный дизайн, правила и ещё не реализованные функции ниже не считаются автоматически выполненными.

**Уточнение 2026-10-18:** пользователь выбрал вариантБ, поэтому ручные привычки/отметки/цели/серии входят в scope(HABIT-001/002,DEC-010). Дизайн/детальная семантика ещё открыты. Текущий этап — UI-каркас на явно демонстрационных данных, затем пользовательское визуальное принятие; не объявлять его полной реализацией Б.

### Предлагаемая первая локальная версия

1. **Сегодня:** время Shorts за день, текущий статус наблюдения, последняя активность, ясное предупреждение о неполных данных/разрешениях. Без фиктивной регистрации и fake server sync.
2. **История:** выбор даты, дневные/недельные итоги и точные локальные интервалы; отдельно показывать gaps/качество, не дорисовывать нулевое использование.
3. **Активность Shorts:** детали/график, описание того, что учитывается/исключено, статус совместимости. Общая модель типов активностей готова к расширению, без произвольных плагинов.
4. **Настройки/диагностика:** включение/отключение отслеживания, переходы в Android Settings с объяснением, тема/часовой пояс (после решения), состояние восстановления. Нет обхода force-stop/OEM-ограничений.
5. **Сохранность:** локальная БД, восстановление незавершённой сессии, миграции и тестируемые правила дня; предложен export/import через явно выбранный пользователем файл без широкого storage permission. Формат/защиту/retention ещё согласовать.
6. **Ручные привычки, отметки, цели и серии — приняты вариантомБ**. Напоминания пока отдельно не выбраны; правила периодичности/пропусков/прошлых правок нужно принять до реального расчёта. В UI показываются demo-цели/серии, не настоящая история. Информационная цель не означает блокировку YouTube.

Друзья/Telegram/server/VLESS/push/RAG — будущие этапы. Нельзя выдавать mock друзей или локальные данные за действующий социальный продукт.

### Предлагаемый визуальный процесс

1. Выбрать стиль по референсам/2вариантам: плотность, светлая/тёмная тема, акцент, карточки/типографика. Дизайн-токены централизовать, а не разнести HEX по экранам.
2. Согласовать список экранов/переходов и простой wireframe **без бизнес-логики**.
3. Собрать Compose UI на явно демонстрационных данных; смотреть в Android Studio Preview и/или собственном APK на эмуляторе/телефоне. Демо не записывается как настоящая статистика.
4. Пользователь утверждает внешний вид и состояния (пусто/нет разрешения/неполные данные/обычная история, крупный шрифт, обе темы), затем подключается реальное хранилище и collector.
5. Малые проверяемые итерации, скриншоты **только нашего UI** по согласованному сценарию, сравнение до/после и Git history. Новый заметный дизайн/поведение сначала согласовать; UI approval не отменяет acceptance tests.

Новые инструменты вроде Figma/внешних сервисов не обязательны. Если потребуется отдельный UI-spec файл/макеты, его место и workflow выбрать вместе с пользователем.

### Предложенный порядок

Пользователь уже посмотрел UI и прислал изменения; повторно не требовать прежнюю фразу открытия. Сейчас зафиксировать literal UI и согласовать неоднозначные шкалы/агрегации. Телефон для этой переписки включать не требуется.

Далее два независимых направления: (1) UI-навигация/profile/cards/таблицы/анимации по принятому описанию, (2) Room/репозитории/сырой Shorts collector/миграции. Это разделение плана, **не фактический параллельный запуск агентов**. Raw storage не должен зависеть от ещё не выбранных цветов/эмоций; вычисления подключаются после принятия. Сервер/bot/VPN не разворачиваются.

Перед реальными данными выбрать final identity/подпись/правила времени. Затем интеграция реальных history/manual values, lifecycle/battery/reboot/upgrade tests и отдельные напоминания/release-публикация. Новый yearly layout пока не придумывать; числовые примеры/предложения не объявлять утверждённой математикой.
