## 1. Shorts limit — source finding и точный UI handoff

Проверена полная цепочка:

`Scoring.cell.canEditGoal` → `SaveGoal(habitId, amount, requestedFrom)` → VM →
`ChronaRepository.setGoal` → immutable `GoalRevision` + outbox → exact-day read model.

- Core **уже** возвращает canEditGoal=true для активной Shorts activity без goal и
  при actual Unknown/Partial. Право зависит от archive, а не completeness/score.
  canEditActual для automatic остаётсяfalse; repository повторно отвергает manual.
- Source current UI имел editor только глубоко внутри «План и оценка», после ряда
  Unavailable пояснений. Core permission bug, который требовал бы выдуманного нового
  алгоритма, не найден. UI sibling/root должен сделать действие лимита заметным и
  не прятать его по `goal==null`, `PlanStatus.UNRESOLVED`, actual/score/emotion.
- **Контракт UI без расширения:** показывать editor по `cell.canEditGoal` независимо
  от actual; `ChronaAction.SaveGoal(habit.id, rawMilliseconds, cell.day)`.
  Ввод в минутах → exact BigDecimal ×60000; canonical unit **duration_ms**, goal API
  не принимает «минуты вместо миллисекунд». Например15.5мин =930000мс. Zero разрешён
  для AT_MOST. При неизменённом дробном display сохранять исходный raw goal, не
  записывать округлённый minute display обратно.
- Source существующего NumberDialog уже имел этот conversion/zero handling;
  UI здесь не редактировался. SaveManualValue/Adjustment для Shorts не добавлены.
- Goal revisions append-only, последняя явно запрошенная revision **этого DayKey**
  читается после reload. Нет carry-forward, recurrence, смены истории всех дней.
- Backend source `Activities` goal_revision принимает AT_MOST0 и не зависит от
  measured actual. API/server не менялись/не вызывались. Это не новый live API test.

JVM-регрессии исполняют actual repository methods через internal fake DAO/transaction
seam: first system habit без goal, Unknown/Partial, create/save/recreate repository/

## 2. Managed build-time server configuration

Обычный пользователь больше не может вызвать смену target: VM ConfigureServer и
верхний AndroidClient.configure отвергают legacy action с SERVER_CONFIGURATION_MANAGED.
Публичное имя action сохранено для совместимости, но не является bypass. UI sibling
убирает editor; production UI/preview здесь не редактировались.

В module Gradle:

- `chronaApiBaseUrl` Gradle property (приоритет) либо `CHRONA_API_BASE_URL` environment.
- Generated `BuildConfig.CHRONA_API_BASE_URL`, buildConfig=true. Default — пустой,
  **никакого fake/private address в source/defaults**. Не задаются token/credentials.
- В supplied value допускается только прежний strict HTTPS authority+safe base path;
  userinfo/query/fragment/traversal/encoding/небезопасные hosts отвергаются **до APK**.
  Generic build error не печатает значение/URI exception cause.
- Gradle и runtime используют один и тот же validation body. Для минимального
  решения без buildSrc/framework body зеркалирован в script и защищён source-parity
  JVM test. При правке policy обе копии обязаны измениться вместе.
- Runtime повторно вызывает ServerOrigin.parse. Невалидная внешняя конфигурация
  fail-closed, без fallback endpoint и без сетевого запроса.

`SessionClient.bootstrap` работает под auth mutex **только** при пустом saved target,
отсутствующей session/pending и чистой binding/scope/wire metadata. Наличие local raw
history само по себе не отправляет её: bootstrap не login, не binding, не sync consent.
Он только сохраняет проверенный target в существующий encrypted vault обычным persist.

Уже сохранённые target/session/pending **никогда не заменяются новым build default**.
Если vault пуст, но SQL profile bound, scope или frozen request уже есть, bootstrap
блокируется с честным notice, не переносит/не очищает данные. Старые origin/account
guards и bounded consent/retry не ослаблены. Нет DB migration/purge/новой схемы.

При пустой сборочной настройке остаётся безопасная локальная версия. Попытка входа
даёт сообщение «В этой сборке не задан сервер… нужна сборка с настройкой сервера»,
а не инструкцию обычному пользователю ввести технический URL.

### Root provisioning

Root должен перед final rebuild **приватно** установить `CHRONA_API_BASE_URL` либо
Gradle property. Значение не помещать в source/docs, command output или build scan;
environment предпочтительнее URL в shell command arguments. Для реальной сборки
**не копировать** test override `-PchronaApiBaseUrl=`: пустая property приоритетнее env.

В этом checkpoint actual target не запрашивался/не читался. Проверочный APK собран
**с пустым bootstrap**; он не заменяет final APK после UI integration и root config.
На обновлении настроенной code3 установки сохранённая session/target должны остаться
приоритетны. Перенос bound profile к другому серверу всё ещё отдельное решение.

отправлен…». Успех остаётся в компактных sync status/last-success/pending count.
Нет общего фильтра ошибок: consent/account-binding/conflict/storage/network notices
сохраняются и unit-проверены. Explicit sharing acknowledgement не менялся как
отдельный permission-related flow; UI оформление остаётся у sibling.

Bounded one-shot approval/retry не менялся. Success не разрешает будущую очередь,
ошибка не ack-ается, raw не удаляется. Регрессия проверяет отсутствие success notice
и сохранение ACCOUNT_BINDING_CONFLICT/CONSENT_SCOPE_CONFLICT notices.
