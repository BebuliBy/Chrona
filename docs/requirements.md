# Требования Chrona

## VPN и частота отправки — уточнение 2026-10-18

Владелец запросил target **5–10с**, желательно без открытого UI, и устойчивость к
включённому VPN/смене связи. Нормальная потеря сети не logout; токены/привязки и
TLS не ослаблять, VPN не обходить. Active-process target не гарантия после OS kill/
force-stop; existing Accessibility + WorkManager fallback, новый foreground режим
с notification/Stop требует отдельного согласования. Пустая friend history не
разрешает автоматически расширять sharing. [Реализация/пределы](vpn-two-account-result-2026-10-18.md).

## Последнее прямое уточнение владельца — 2026-10-18

Заменяет противоположные прежние указания ниже;7эмоций/формулы/Shorts read-only
не пересогласуются:
- Обычные экраны без служебных статусов/raw timestamps/gaps/coverage-простыней,
  легенд/tutorial. Важные ошибки/разрешения/доступ друзей остаются.
- Длительность ч/мин/с без нулевых частей; интервалы — local time без milliseconds/Z.
  Лимит Shorts меняется явно, actual только системой.
- Сегодня выделено в неделе/месяце независимо от оценки, «Настройки» не переносятся.
- Endpoint управляется сборкой, недоступен пользователю для просмотра/редактирования.
- **Автосинхронизация**, включая новые записи после login, без popup на каждую
  отправку. Persistent account toggle, binding/idempotency/ACK и отдельные права
  sharing сохраняются; Android background best effort.
- Shorts оценивается по **накопленному записанному времени сейчас**, прошедший день
  показывает свой итог. Partial не блокирует лицо/оценку; empty automatic counter=0,
  missing manual остаётся Unknown; неизмеренное время не дорисовывать.
- Жёлтые7лиц с мягкими анимациями в духе Telegram, не обещание точных Telegram assets.
- По просьбе владельца мелкие правки этого этапа без дополнительных тестов и
  повторных диагностик; сборка APK нужна для установки. [Итог](ux-installed-2026-10-18.md).

Дата исходной версии: 2026-10-17. Основание: описание пользователя и последующие явные ответы. «Согласовано» означает продуктовую цель, **не** техническую реализованность. Базовый Shorts-прототип проверен ограниченными реальными сценами, полноценная локальная Chrona ещё не реализована; [результаты](spike-results-2026-10-17.md).

### Согласованные математические правила — 2026-10-18

Пользователь явно подтвердил пункты1–5 предыдущего объяснения. Таблица/формулы ниже **приняты**, но в приложении пока не реализованы. Первоначальная пауза снята DEC-015; фактические продуктовые работы через High ещё не запущены.

| Эмоция | Полезная: p=100×actual/goal | Вредная: p=100×actual/limit |
|---|---|---|
| Слёзы | 0≤p<25 | p>400 |
| Сильная грусть | 25≤p<50 | 200<p≤400 |
| Небольшая грусть | 50≤p<75 | 150<p≤200 |
| Ровный рот | 75≤p<100 | 100<p≤150 |
| Улыбка | 100≤p<150 | 50<p≤100 |
| Большая улыбка | 150≤p<200 | 0<p≤50 |
| Звёзды | p≥200 | p=0 |

Подтверждены все промежуточные границы: у полезной0≤p<25—слёзы (не только при полном0); у вредной50<p≤100—улыбка. Actual сохраняется без обрезания по goal; ограничение цветового score не ограничивает данные или эмоции перевыполнения.

**Цвет и ячейки (пункт2 принят).** Для известных фактов плановых привычек/дней вводится score q∈[0,1]. При actual A≥0 и положительном плане G:

- полезная: `q = clamp(A/G, 0, 1)`;
- вредная: `q = 1` при `A≤G`, иначе `q = clamp(2−A/G, 0, 1)`; т.е.1,5×лимита→50%,2×лимита→0%;
- `clamp(x,0,1)` ограничивает только оценку, не actual;
- в полностью наблюдаемом выбранном периоде `S = 100×mean(q)` с одинаковым весом каждой запланированной habit-day ячейки; не average по всем периодам жизни;
- цвет S0—бордовый,S50—жёлтый,S100—зелёный, плавные приглушённые оттенки между ними, пересчёт по исходному дробному S без раннего округления;
- сверх100%цвет не уходит: избыток одной привычки **не компенсирует** провал другой; избыток виден в числе/эмоции/кривой;
- известный q=1—галочка, q=0—крест,0<q<1—процент. Unknown/неплановые дни не подменяются известным0; для неполного покрытия требуется явный статус, его точная агрегация отдельно OPEN-COVERAGE.

**Кривая (пункт3 принят).** От начала выбранного периода накапливаются signed deviations; y=0—выполнение ровно по плану. Для отдельной привычки показывать сумму `(A−G)` в её единицах, для вредной знак наоборот. Для общего графика суммировать по плановым привычкам/дням **нормированные** отклонения `(A−G)/G`, для вредных `(G−A)/G`, при G>0; ось **«доли плана»**, не сумма страниц+минут и не процент выполнения периода. Верхний cap цветового score не применяется к кривой. Пользователь признал ошибку примера: +20страниц ежедневно за7дней→**+140**, не170.

**Нулевой лимит (пункт5 и последующее уточнение приняты).** Вредной разрешён лимит0. При достоверно известном A=0 лимит соблюдён, **100% выполнения/q=1**, как явно уточнил пользователь. Любое A>0 — нарушение по ранее принятому бинарному правилу. Отсутствие наблюдения не является известным0 и не даёт автоматические100%. Это оценка выполнения, **не** отношение actual/limit: actual/0 и «процент превышения» не вычислять. Конкретный вклад нулевой ветки в общую нормированную curve остаётся OPEN-ZERO-CURVE, уточнение100% не выбирает его коэффициент. Таблица эмоций выше определена приG>0; отдельное отображение нулевой ветки не подменять процентом использования. Дробная точность/расписание/goal revisions отдельно уточняются.

**YouTube read-only (пункт4 принят).** На прямой вопрос о ручном исправлении пользователь ответил **«С shorts не разрешаем, там работает исключительно наша система»**. Факт YouTube — только collector/системный расчёт из интервалов, никаких manual overrides/adjustments, даже с пометкой. Это ограничение write API/repository и UI, не только спрятанная кнопка. План/лимит — отдельная настройка, не ручной факт.

## Смысл метрики и границы

- Согласован приоритет **открытого экрана Shorts**, не доказанного воспроизведения или внимания. AccessibilityService-прототип показал принципиальную возможность на одном устройстве/версии в базовых сценах; это не гарантия готовности продукта/точности/всеверсионной совместимости.
- Уточнение пользователя: маленькое плавающее окно **исключено** (DEC-006). Прежнее предложение учитывать его не было принято; OPEN-WINDOW о выборе правила закрыт. Техническое покрытие режимов остаётся отдельным вопросом.
- Время предупреждения лимита также **исключено** (SHORTS-004/DEC-007); OPEN-OVERLAY о выборе правила закрыт явным подтверждением, не задним числом под реализацию. Прочие overlays/реклама/unknown остаются отдельными сценариями.
- Допустимые частные условия пользователь готов уточнить по результатам прототипа. Это не разрешает молча заменить Shorts временем всего YouTube или другую существенную смену метрики.
- Интервалы — события активности пользователя, которыми он разрешил делиться. Это не разрешение собирать тексты UI, ролики, чаты, нажатия клавиш или полную техническую телеметрию.
- Точная запись timestamps не означает такую же доказанную точность детектора. Показывать неполноту/неуверенность; неизвестное не равно нулю.
- Отзыв доступа прекращает новые чтения и дальнейшую отправку. Уже увиденное/доставленное в Telegram нельзя гарантированно отозвать.

## Не входит в ближайший этап

RAG, Play, произвольные плагины/микросервисы и дополнительные неописанные команды бота. Пользователь отдельно разрешил серверные действия/sudo: proxy/DB/API/private HTTPS выполнены и проверены в указанном scope; token/BotFather/реальный phone E2E ещё нет. Source и partial server checkpoint не отменяют оставшиеся продуктовые вопросы. Отдельно согласовывать чужие сервисы/данные, глобальную сеть, новые аккаунты; ключи никогда не публиковать. Phone discovery требует отдельного consent/защиты от перебора.
