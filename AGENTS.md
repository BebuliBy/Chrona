# Работа с Chrona

## С чего начинать

Прочитай README.md, docs/requirements.md, docs/decisions.md, docs/roadmap.md и относящиеся к задаче разделы docs/architecture.md и docs/accessibility-spike.md. Соблюдай применимые более высокие инструкции. Убедись, какие требования согласованы, а какие детали остаются открытыми.

## Требования и изменения

- Не отклоняйся от согласованных требований и не переписывай их задним числом ради удобства своей реализации.
- Обсуждение, идея агента, черновик, существующий код или успешная сборка не являются согласием пользователя на изменение продукта.
- Если код, README, связанные документы или новый запрос противоречат друг другу — объясни расхождение и уточни решение до затронутой реализации.
- Существенные продуктовые/архитектурные изменения сначала предложи с последствиями и получи принятие пользователя. Только затем обнови решение/требования и выполняй одобренный объём.
- Можно без отдельного обсуждения отразить точные факты выполнения уже согласованной работы и исправить опечатку без изменения смысла. Не выдавай запланированное или экспериментальную гипотезу за реализованное/проверенное.

## Завершение этапа

После согласованной реализации обязательно обнови относящиеся документы, roadmap, CHANGELOG и результаты проверок. В отчёте укажи пути, команды/результаты, ограничения и нерешённое. Работа не полностью завершена при устаревшей оговорённой документации. Требования имеют отдельный статус согласования, выполнение — отдельный статус проверки.

## Текущая граница

- Первый этап — локальная проверка AccessibilityService и экрана Shorts. Не подменяй её учётом всего YouTube или сетевого трафика.
- Доступ друзей включает согласованные интервалы активности, но только разрешённые владельцем типы; правило «только дневные суммы» не является требованием проекта.
- Тексты, названия роликов, переписки, полные UI-деревья, скриншоты и секреты не собирать/не сохранять для обычного учёта. Любую дополнительную диагностику сначала обосновать, ограничить и согласовать.
- Не включай разрешения на телефоне вместо пользователя, не обходи Android restricted settings/защиты, не скрывай наблюдение. Принудительную остановку не обходить.
- По просьбе пользователя явно говори, когда нужно включить/разблокировать телефон и какой экран открыть. Для размеченного теста дождись подтверждения нужного экрана; наличие ADB-соединения само по себе не доказывает состояние UI.
- Backend/bot deployment и серверный VLESS, новые системные пакеты, работа с аккаунтами и реальными данными — отдельные согласуемые действия, не следствие наличия этого README.
- Git-порядок этого проекта задан ниже прямым постоянным разрешением пользователя. Не коммить local.properties, .env, токены, keystore и приватные логи. Память команды не заменяет проектную документацию.

## Постоянное разрешение Git для Chrona

Пользователь 2026-10-17 явно поручил создать/использовать `dev`, отправить проект и после изменений делать осмысленный commit и push. Последние явные уточнения: название приложения **Chrona**, актуальный remote **`git@github.com:BebuliBy/Chrona.git`**. Прежний MyChrona.git заменён до первой отправки; не использовать устаревший адрес и не переименовывать GitHub-репозиторий самостоятельно.

- После каждого завершённого согласованного набора изменений (код, тесты или документация) проверить результат, фактически обновить документацию, создать содержательный коммит и выполнить `git push origin dev`. Это не коммит на каждое нажатие клавиши и не пустые коммиты при отсутствии изменений.
- Рабочая ветка по умолчанию `dev`, origin — ровно указанный репозиторий. Перед push сверить branch/remote/upstream; смена назначения, merge в main, force-push и удаление веток требуют отдельной просьбы.
- Перед коммитом проверить `git status`, содержательный `git diff`/staged diff и доступную историю. Стадировать только относящиеся файлы; не включать чужие незавершённые изменения, сборки, SDK, дампы, локальные данные и секреты.
- Сообщение коммита коротко объясняет смысл/результат изменения; новая функция, исправление и документация должны отличаться по смыслу. Не подменять описание общим «update».
- Проверить успех push и совпадение локального коммита с remote branch. При ошибке сохранить локальную работу, сообщить причину и оставить доставку открытой; не обходить hooks/защиты, не делать force и не скрывать непроверенное.
- Git выполняет только корневой ответственный участник. Дочерние помощники возвращают файлы/проверки без commit/push. Разрешение относится **только к этому проекту и указанному remote**, не ко всем репозиториям, deploy/публикации APK/аккаунтам или системным изменениям.
